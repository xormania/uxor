## Configuration ownership and intentional repetition

- Each recipe manifest remains native owner for copy roots and recipe/Composer requirements. Equal dependency arrays express independently installable recipes; a root tooling Composer manifest cannot replace them. Catalogs/README installation directives should read these values, as the existing demo already does.
- Root `manifest.json` owns kit identity and Flowbite CSS compatibility declaration. NPM and importmap entries are native delivery representations, not different projects. Dependencies' supported ranges, application locks, CI matrices and image contents remain distinct decisions.
- Root `kit.css` and `theme/assets/styles/uxor.css` are intentionally duplicated delivery surfaces with an existing byte-equality check. Keep a clear source and deterministic copy/equality gate; do not promise a new framework merely to remove one copy.
- Shared JS helper ownership stays in assets-only recipes with native dependencies. The passed import checker provides executable relationships; `packages/uxor/` should not own app runtime imports.
- The 52 repeated attribute guards in this subset are app-owned template payloads. Runtime centralization into a package-only PHP helper would make installed recipes depend on a development package and violate removal-of-dev-dependencies acceptance. Prefer existing hostile-props behavior and parity checks over an unsafe extraction.
- `App\UXor\…`, `flowbite_*` Twig/filter/form symbols, controller names, copied paths and theme role utilities are consumer runtime contracts. Rename the former tooling package namespace/resource URI/CLI while preserving these UI interfaces unless a separately versioned API change is deliberately chosen.
- Per-request CSP nonces, native application route/session/storage policy, form types, authentication user stores and authorization stay app-owned. Shared config must not silently redefine them.

## Finding UXOR-AUD-PROD-008: accepted rich-text HTML can exceed the policy's readable limit after sanitizing

- **Class:** bounded correctness defect; source-confirmed control-flow mismatch, runtime reproduction unavailable.
- **Priority / effort / risk:** P2, small-to-medium; medium behavior risk because resolving it must preserve no truncation and existing safe output.
- **Observed:** [editor/src/UXor/Editor/EditorHtmlPolicy.php:67–81](https://github.com/xormania/uxor/blob/40d957cd1ea7766ac0dee742816948ce5ae05bc3/editor/src/UXor/Editor/EditorHtmlPolicy.php#L67-L81) refuses an input above 1,000,000 bytes. The sanitizer intentionally uses an unlimited later-pass sanitizer at lines 43–63 because entity escaping can expand output. [demo/tests/Editor/EditorHtmlPolicyTest.php:154–165](https://github.com/xormania/uxor/blob/40d957cd1ea7766ac0dee742816948ce5ae05bc3/demo/tests/Editor/EditorHtmlPolicyTest.php#L154-L165) explicitly asserts that a sanitized value can exceed that 1,000,000-byte readable limit while remaining whole. [editor/src/UXor/Editor/EditorType.php:32–44](https://github.com/xormania/uxor/blob/40d957cd1ea7766ac0dee742816948ce5ae05bc3/editor/src/UXor/Editor/EditorType.php#L32-L44) checks the original input's `max_bytes`, sanitizes it and checks text characters, then returns that expanded HTML as model data; supported options permit `max_bytes` up to 1,000,000 and any integer `max_chars` (lines 61–74).
- **Concrete source-derived case:** configure `max_bytes = 1_000_000` and `max_chars = 300_000`; submit `<p>` followed by 300,000 raw ampersands and `</p>` (300,007 original bytes). Escaping yields about 1,500,007 bytes of accepted model HTML, while its 300,000 text characters fit the chosen limit. A later `EditorType` model transform calls the same policy at line 31; `EditorExtension.php:23` also calls it on output. Both refuse the now-oversized stored value. The standalone component instead sees the value as unreadable (`Editor.html.twig:37,111,114`) and shows an empty editor/textarea. This requires raising the ordinary form byte/text limits, or direct policy use; no failure at default field limits is asserted.
- **Inference / impact:** an application can accept/store content its normal output/edit path cannot display; the recipe README's statement that sanitizing its output is unchanged ([editor/README.md:54–56](https://github.com/xormania/uxor/blob/40d957cd1ea7766ac0dee742816948ce5ae05bc3/editor/README.md#L54-L56)) has an unhandled size boundary. This is not an XSS claim.
- **Recommendation:** define an explicit persisted-output/readable-size contract. Reject an expanded value with a field error before saving, or support a separately bounded trusted canonical-output path; do not cut markup and do not remove the defensive source limit. Document any revised supported range.
- **Acceptance:** a form-save-load-output regression using expanding HTML and supported raised options must either reject with a useful field error before persistence or render/edit the entire saved value successfully. Retain existing tests for hostile HTML removal, fixed allowed schemes/rel, no truncation, canonical idempotence, bytes versus characters, and the over-limit Live fallback.
- **Consumers / propagation:** `EditorType`, `EditorHtmlPolicy`, `EditorExtension`, Editor Twig widget, README and installed application copies; source checks, form tests and a production-style consumer roundtrip are necessary. The proposed package migration should carry this as a separate recipe fix rather than silently change imported application content.

The template's `|raw` is applied only to renderer output (`MarkdownEditor.html.twig:55–63`).

**Tests read:** policy hostile markup/links/idempotence/whitespace/counts and nontruncating escaping; editor form byte/character/error/preserved input, Live unreadable/maximum input; Markdown hostile/raw/images/links/nesting/delimiters/expanded output, form byte/character/CRLF/preserved errors and oversized submit, Live counters and bounded preview. ## Configuration ownership and identity implications

The direction documents select one repository and package implementation under `packages/uxor/`, while retaining Toolkit recipe installation into application-owned files. The existing public recipe identities include `App\\UXor\\...`, `flowbite_editor_html`, `flowbite_editor_readable`, `flowbite_markdown_html`, `flowbite_editor`, `flowbite_markdown`, copied JS controller names and local asset paths. The new tooling's intended `Xormania\\UXor\\` namespace/`uxor` CLI is a different delivery surface. A blind global rename would break installed callers and require unplanned migrations.

| Decision | Existing owner | Consumers | Proposed treatment |

## Suggested implementation order

1. Carry existing security, lifecycle and install contracts into the imported package's generated reference tests; do not change recipe ownership or public names as part of tooling identity migration.
2. Ensure both shared-archive consumers retain every recipe runtime payload and both Google images; development screenshot/test exports remain separate. Verify a fresh independent consumer from the actual candidate archive and its production dependency mode.
3. Land UXOR-AUD-PROD-008 as a small recipe correction with explicit documented output-size semantics and a form-save-reload test, preserving no truncation.
4. Run the optional named-control/Turbo probe before assigning any extra finding or regression test; do not infer a defect from a missing example alone.
