# UXor CI, workflows, actions, and release audit

Audit date: 2026-10-16, America/New_York. UXor source baseline: `40d957cd1ea7766ac0dee742816948ce5ae05bc3` (`dev`). This is a read-only source audit and future change inventory; proposed Composer package integration is not implemented. Working project is UXor; Xorder supplies supporting development resources.

Evidence key: **observed source** means the pinned checkout was read; **local reproduction** means existing tooling ran against controlled inputs outside the checkout; **inference** means a consequence of source/event contracts without an observed production incident. The [governance report](06-governance.md) and [coverage and evidence report](09-coverage-and-evidence.md) record effective GitHub settings and historical run sampling; observed live evidence takes precedence over workflow comments. No workflow dispatch, publication, issue/comment, setting update, tag movement, or registry mutation was performed.

## Assessment

The current coordinator is a strong starting point: every branch push has an aggregate check, the changed-path classifier comes from the branch's merge-base with `dev`, unknown inputs select conservative Toolkit work, renamed/deleted paths are considered, full runs remain on `dev` and `main`, matrix fail-fast is disabled, the image-cache writer is separate from test jobs, and privileged diagnosis reads data outside its trusted checkout. Release planning rejects a tag at another commit, reads notes at the selected historical release commit, and separates consumer installation from the contents-write job. Existing tests exercise real shell release steps with writes stubbed; they do not prove live GitHub permissions or remote installation.

The planned Composer package has no current CI, dependency audit, consumer integration, or Packagist route in this checkout. Those are migration requirements, not regressions. Existing diagnostic provenance is incorrect for schedules that execute `dev` while their event SHA is the default branch; Monthly also resolves mutable `dev` independently in every job. The source says branch freshness is required, while live ruleset evidence shows `dev`'s strict status-check policy disabled; push-only checks therefore do not establish validation of the eventual merge with a newer base. Keep that governance delta coupled to CI policy, without claiming static comments establish live protection.

## Selection, caches, diagnostics, and trust traces

The Changes job uses full checkout history and `git merge-base HEAD origin/dev`, not last pushed commit or PR base payload. For a work-order job, this intentionally validates the cumulative feature work since dev, including previously merged parts. `git diff --name-only --no-renames` includes both old and new path for renames and deleted files, tested by scratch Git fixtures. Missing merge-base/script selects full work. Classification logic is read from base; executable head classifier tests still run so changes to the classifier itself are checked. Head workflow defines orchestration; base-classifier isolation is not a sandbox against arbitrary workflow edits, which depend on review/protection.

GHA scopes are retained as explicitly permitted fallback references though no current producer writes them; workflow-cache test intentionally accepts this when written registry source precedes them. Keep future root package/demo/independent consumer cache roots separate. A registry layer cache does not prove archived source ran tests.

Diagnostics preserve first failed and recovered attempts, test identities/locations/durations, invalid/missing/setup statuses and global errors. Shard planner rejects missing list/errors/duplicate/drop, includes serial/unnameable-title whole-file fallbacks, computes common timing split, and re-lists with real Playwright to verify its own selected IDs. Coverage below50% timings falls back to count split; refresh below90% is advisory. Timing input from successful dev run is schema/numeric validated, selects only partition sizes, and cannot itself omit a listed test in timing mode because partition+real list verification are gating.

Jev reads source run/attempt only and never executes the producer artifact. Names/shards passed as quoted shell data; bounded input JSON/logs, HTTPS endpoint, no redirects, secret/environment-value and structured-field redaction, strict response/model/probability validation, elapsed/request/response/attempt limits, static category/excerpt choices, and escaped GitHub annotations. No provider response overrides verdict or authorizes retry. Environment/branch controls protecting access to the key need live settings evidence; code currently references a repository-context secret with no environment binding. Never print values to audit them. Source-attempt metadata currently has no actual checkout SHA, leading to the provenance finding below.

Failed/cancelled source jobs stay failures. Reports/artifacts mostly use `!cancelled()` to keep evidence after failure but may not survive cancellation. Jev collectors are advisory and some run even on recovered flaky tests. Missing PHP/Tool JUnit setup failures or noncaptured action failures yield no diagnosis; this does not turn original checks green. Monthly screenshot pass uses PW_SCREENSHOTS=all after behavior run and rewrites results.json only after behavior artifact saved, preserving their distinction. Its screenshot parser enforces complete engine/shard report before totals. Timings and coverage values are intentionally advisory, so green Monthly must not be described as reaching an MSI/coverage/performance threshold.

## Release dependency and recovery map

1. Release PR dev→main finalizes changelog version and generated links. Ordinary CI is push/head-source check; Release checks on PR reads synthetic merge. The [governance report](06-governance.md) reconciles observed main required checks, freshness and merge method, and records inaccessible effective settings; comments are not live enforcement.
2. A successful same-repository CI push to main triggers Release. Manual Release on main skips the successful-CI predicate. Check job runs trusted current main scripts, reads event CI head SHA as history, and checks it remains main ancestor.
3. Missing GitHub releases are identified from CHANGELOG at that event source SHA. `release-plan.sh` finds each heading's first addition on ref first-parent history; notes read at that historical candidate. Existing lightweight/annotated tag must resolve to exact candidate. Planning failure happens before installation/writes.
4. Only newest missing release **when untagged** gets Toolkit install test via KIT_REF=candidate SHA and today's trusted Docker scenario/fixtures. Current native archive check is CI, not a proof the same historical release candidate passed all Composer/Toolkit routes. Correctly tagged newest gets GitHub Release without rerunning installation; historical correctly tagged releases are best effort and do not get today's recipe-dependent scenario.
5. Separate write job checks out current main, revalidates event source ancestry and recomputes plan, reads only check outputs not executable files/artifacts. For untagged newest requires checked=candidate; creates annotated tag then push with scoped token; creates verified-tag latest GitHub Release. Overlapping run release already exists → skip; unexpected tag at another commit → fail. Group serializes write job, not candidate checks.
6. Pages call receives check's event source commit, which can differ from historical version-heading candidate when main advanced without a new heading. Page build uses selected source with fetched tags and release metadata. Current flow intentionally builds after missing release publication. Full all-new rerun once every Release exists no longer calls Pages; rerun failed Pages job/manual main rebuild repairs it.
7. No root Composer publication, refresh dispatch/reusable flow, SAFE token binding, asynchronous indexing poll or source-reference assertion exists. GitHub token-created tag does not ordinarily trigger another push/tag workflow, so call Packagist refresh directly from release flow (or explicit dispatch), with same-tag retry entry point.

Proposed publication flow: candidate plan → both distribution route tests/installed consumer and immutable evidence manifest keyed candidate SHA + check policy version → trusted write job verifies candidate and creates tag/release → dedicated narrow refresh job holding only Packagist SAFE binding → bounded poll until expected version's `source.reference` equals candidate and intended package identity is visible. Refresh HTTP success queues work, not indexing proof. Retry takes existing immutable tag, verifies tag→source/proof, refreshes/polls same release. Do not execute candidate dependency install alongside publication credentials. Preserve historical Toolkit-only tags, use next unified project version with new root Composer metadata; no version field in composer.json. Existing public archive/install compatibility must survive package import.
